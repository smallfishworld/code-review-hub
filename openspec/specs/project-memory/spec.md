# project-memory Specification

## Purpose
平台按仓库维护随评审积累的项目记忆：评审前检索注入相关记忆帮助引擎理解工程背景与规避已知误报，评审后从结果与人工反馈中蒸馏新记忆，使同一工程的评审随使用次数增多而更准、更快。记忆对用户完全可见可编辑，任何自动写入都可追溯来源任务。

## Requirements

### Requirement: 记忆条目模型

每个仓库 SHALL 拥有独立的记忆集合，条目字段 MUST 包含：类型（architecture / convention / pitfall / suppression / history / glossary 六类之一）、作用范围（路径前缀或模块名，空表示全仓库）、标题、正文、置信度（0–1）、检索命中次数、人工确认次数（与检索命中独立计数）、误报指纹（suppression 类必填，其余类型可空：由文件路径前缀与问题特征归一化生成的稳定标识）、状态（active / archived / rejected）、来源任务（可空）。条目 MUST 同时持久化为 markdown 文件（`<DATA_DIR>/memory/<repo-id>/` 下按类型组织）与 SQLite 索引（含 FTS5 全文索引，分词方式 MUST 对中日韩文本有效）；两者以 SQLite 为准，markdown 可随时从索引重建，用户手工编辑 markdown 后平台 SHALL 提供重新加载入口。

#### Scenario: 查看仓库记忆
- **WHEN** 用户打开仓库详情的项目记忆 tab
- **THEN** 展示该仓库全部记忆条目（类型、范围、标题、置信度、命中次数、状态）及其来源任务链接

#### Scenario: 手动编辑记忆
- **WHEN** 用户在记忆 tab 编辑、停用或删除某条记忆
- **THEN** 变更即时生效于后续评审的检索，且 markdown 文件同步更新

### Requirement: 评审前检索注入

评审任务启动前，平台 SHALL 自行采集本次评审的变更文件列表与新增行标识符（SVN / Git diff，于工作副本更新至目标节点后、评审执行前完成）作为检索输入；采集失败时降级为仅全仓库作用域 + 全文匹配，MUST NOT 使任务失败。检索按作用范围前缀匹配 + FTS 全文匹配召回，按 置信度×时间新近度×命中次数 排序，注入内容截断至固定 token 预算（默认 1500，按中英混合字符保守估算）。注入经由引擎能力声明的通道（ocr 为 `--requirement` 业务背景参数）；引擎不支持注入时 MUST 跳过且任务正常执行。每次实际注入的条目集合 MUST 记录到任务（注入审计），被注入条目的命中次数与最近命中时间 MUST 更新。

#### Scenario: 命中抑制记忆
- **WHEN** 变更文件命中一条 suppression 记忆（此前被人工确认的误报模式），且任务引擎为 ocr
- **THEN** 该记忆内容随业务背景一并发给引擎，注入审计记录该条目

#### Scenario: 记忆为空或引擎不支持
- **WHEN** 仓库没有任何 active 记忆，或引擎记忆注入能力为 none
- **THEN** 评审正常执行，不注入，任务详情不展示记忆统计

#### Scenario: 预算截断
- **WHEN** 召回的记忆内容总量超过 token 预算
- **THEN** 按排序得分从高到低保留，超出部分不注入

### Requirement: 报告确定性抑制

对归一化后的评审 issue，平台 SHALL 按该仓库激活的 suppression 记忆执行确定性过滤：issue 的文件路径与问题特征命中某条 suppression 的误报指纹时，该 issue MUST 在报告入库前被标记为已抑制（记录命中的记忆条目），默认不展示于报告视图与通知，并可在报告详情展开查看。抑制动作 MUST 确定性执行、不依赖评审引擎对注入内容的遵从。

#### Scenario: 误报模式被确定性抑制
- **WHEN** 一条 issue 命中已有的 suppression 指纹，且该次评审引擎未理会注入的抑制提示仍报出该 issue
- **THEN** 报告默认视图与通知不包含该 issue，报告详情可展开查看被抑制条目及其命中的记忆

#### Scenario: 无命中不误伤
- **WHEN** 仓库没有任何激活的 suppression 记忆
- **THEN** 报告与通知行为与现状一致

### Requirement: 评审后蒸馏写入

评审任务成功后，平台 SHALL 触发记忆蒸馏：将本次变更与评审发现交给 LLM 按严格结构输出候选记忆，单次蒸馏 MUST 限额（每次评审最多新增 3–5 条）；候选条目与既有记忆合并——同类型同范围内标题语义相近时更新已有条目（置信度加权平均）而非新增。蒸馏失败（LLM 不可用、输出不合规）MUST 不影响评审任务本身的结果与报告。

#### Scenario: 蒸馏产出新约定
- **WHEN** 一次成功评审中 LLM 蒸馏出 2 条新的 convention 候选
- **THEN** 2 条以低置信度写入该仓库记忆，markdown 同步生成，来源任务可追溯

#### Scenario: 与既有记忆合并
- **WHEN** 蒸馏候选与既有条目同类型同范围且标题相近
- **THEN** 更新既有条目正文与置信度，不产生重复条目

#### Scenario: 蒸馏失败不影响任务
- **WHEN** 蒸馏阶段 LLM 调用失败
- **THEN** 评审任务状态保持成功、报告完整可浏览，仅记忆不更新（失败原因记录在蒸馏日志）

### Requirement: issue 反馈闭环

报告的每条 issue SHALL 提供「误报」「已修复」与「不修复」反馈操作（登录用户可用）。标记误报 MUST 生成或强化一条 suppression 记忆：按误报指纹判定「同一模式」——指纹相同的反馈聚合到同一条 suppression（含文件匹配范围、原因、来源 issue），其人工确认计数独立于检索命中计数单独维护，确认计数每达到 3 的倍数时置信度 MUST 按规则提升。标记已修复 MUST 生成一条 history 记忆。标记不修复 MUST 要求填写理由，并生成一条 pitfall 记忆。每条反馈 MUST 记录到 review_feedback 表并关联其生成或强化的记忆条目，可追溯。同一问题重复提交相同处置 MUST 返回原结果，提交冲突处置 MUST 返回 409。

#### Scenario: 标记误报
- **WHEN** 用户对某条 issue 点击误报并提交原因
- **THEN** 生成 suppression 记忆并在下次评审前可被召回注入；该 issue 标记反馈状态

#### Scenario: 重复误报提升置信度
- **WHEN** 同一误报指纹累计第 3 次被标记误报
- **THEN** 对应 suppression 条目人工确认计数达到 3，置信度按规则提升，注入排序更靠前

#### Scenario: 后续评审召回不修复决定
- **WHEN** 后续评审召回已标记「不修复」的问题
- **THEN** 平台向评审引擎提供原问题位置和当前保存的理由，要求引擎仅在理由失效或风险条件实质变化时重新报告，并给出证据

### Requirement: 记忆演化与治理

平台 SHALL 实施记忆演化规则：人工确认（反馈闭环）提升置信度、长期未命中降低置信度；90 天未命中且置信度低于阈值的条目自动归档（不删除）；每完成 20 次评审触发一次 compaction（合并重复、重写项目画像概览），compaction MUST 限额且结果可审计。所有演化动作（归档、合并、置信度变化）SHALL 在记忆 tab 可见。

#### Scenario: 自动归档陈旧记忆
- **WHEN** 某条 active 记忆超过 90 天未命中且置信度低于阈值
- **THEN** 下一次演化检查将其置为 archived，不再参与召回

#### Scenario: compaction 合并重复
- **WHEN** 仓库累计完成第 20 次评审触发 compaction
- **THEN** 重复条目被合并、条目总数下降或持平，动作记录可查

### Requirement: 冷启动项目画像

对尚无记忆的仓库，平台 SHALL 提供项目画像生成：扫描仓库工作副本，产出 architecture / convention 类的基础记忆（技术栈、模块划分、构建与测试方式、关键约定），并生成 `profile.md`。画像生成 MUST 手动触发（仓库详情按钮）且可重复执行（覆盖更新）。

#### Scenario: 首次生成画像
- **WHEN** 用户对新仓库点击生成项目画像并等待完成
- **THEN** 该仓库出现 architecture/convention 类记忆条目与 profile.md，后续评审默认注入其中相关内容

#### Scenario: 重复生成
- **WHEN** 用户对已有画像的仓库再次点击生成
- **THEN** 基础类记忆被更新而非重复新增

### Requirement: 记忆查询 MCP 桥

平台 SHALL 提供只读的记忆查询 MCP 桥进程（stdio），在评审时由注入器自动提供给支持 MCP 的引擎。桥 MUST 仅暴露三个只读工具：`memory_search`（按查询词召回，可按记忆类型过滤，返回条数有上限）、`memory_get`（按 id 取单条全文与来源任务）、`memory_stats`(该仓库记忆统计)。桥 MUST 以只读方式打开平台 SQLite（WAL 多进程读），且其可见范围 MUST 被强制限定在单一仓库（由注入器经环境变量提供，工具参数不接受仓库标识）。桥 MUST 复用与预注入一致的召回与排序逻辑（置信度 × 新近度 × 命中，低置信度门槛），输出 MUST 有长度上限。桥进程故障或记忆库不可用 MUST NOT 影响评审任务本身（工具返回明确错误文案）。

#### Scenario: agent 按需查询误报历史
- **WHEN** 评审 agent 在循环中调用 `memory_search`，query 命中该仓库某条 suppression 记忆
- **THEN** 工具返回该条目的标题、正文（人工写的误报原因）、置信度与来源任务链接，ocr 的 MCP 循环正常把结果送回模型

#### Scenario: 仓库隔离不可跨越
- **WHEN** agent 尝试用另一仓库的记忆 id 调用 `memory_get`
- **THEN** 返回未找到，且任何工具在任何参数下都不会返回其他仓库的条目

#### Scenario: 记忆库不可用时评审不受影响
- **WHEN** 桥无法只读打开数据库（文件缺失 / 锁超时）或桥进程崩溃
- **THEN** 工具返回明确的不可用文案（或该 MCP 服务器不可用），评审任务照常完成，报告与通知不变

#### Scenario: 输出有界
- **WHEN** `memory_search` 命中大量条目或单条正文超长
- **THEN** 返回条数不超过上限（默认 5，最大 10），单条正文被截断到上限长度
